# Execution contract

`pump [options] <command> [arguments...]` is the command-line form. Options are `Pump-Me` parameters written by their exact name, before the command. The command and every later token are passed verbatim, so native options such as `-c Release`, `-o out`, `-v q` or `-p:Name=Value` reach the program unchanged. A script block or dictionary after the command is a misplaced option and fails before execution.

PowerShell removes the first `--` of every function call. When the native arguments contain `--`, write one before the command as well: `pump -- git checkout -- main`. A `--` removed after the command fails before execution; it is never silently dropped.

`Pump-Me` takes the same parameters as an advanced function. PowerShell binds them anywhere on the line and claims native options that match or abbreviate them (`-c` is ambiguous, `-v` becomes `-Verbose`), so pass native arguments to `Pump-Me` through `-ArgumentList`.

Without callbacks, the command and its arguments resolve a route. Providing `-OnRecord`, `-OnBatch`, or `-OnStdOut` and/or `-OnStdErr`, bypasses routing. The callback interfaces are exclusive.

Direct options: `ArgumentList` (`Pump-Me` only), `WorkingDirectory`, `Environment`, `InputText`, `State`, `Complete`, `StdOutDelimiter`, `StdErrDelimiter`, `Encoding`, `SuccessExitCodes`, `TimeoutSeconds`, `CancellationToken`, `MaxRecordCharacters` and the output controls (`AsObject`, `AsJson`, `AsYaml`, `MaxItems`, `MaxOutputBytes`, `ExcerptLines`).

The child inherits the environment. Overrides apply only to the child; a null value removes a variable. Arguments are passed as an argument vector without an implicit shell.

An already cancelled token prevents process startup. Cancellation during execution terminates the owned process tree and retains a distinct `Cancelled` outcome. A timeout terminates the owned process tree; five seconds after the deadline pending reads are cancelled and any stream still open (for example held by an orphaned grandchild outside the tree) is abandoned, so the call returns with an incomplete source. Contributors must forward the call's cancellation token to their subprocesses.

The two byte streams are read concurrently. Callbacks execute sequentially in observed order; order within each stream is preserved. There is no guarantee of the original cross-stream write order.

After a record callback fails, the runner continues draining both streams without invoking further record callbacks. The finalizer still receives the retained state and execution metadata.

- `OnRecord`: `param($record, $state)`; the record has `Stream`, `Text`, `Sequence` and `Truncated`.
- `OnBatch`: `param($records, $state)`; the records `OnRecord` would receive, one batch per call, in the same order and from both streams. Batch sizes depend on how fast the child writes and are not specified; an empty batch is never passed, and a replay passes each recalled stream as one batch. One call and one diagnostic check per batch instead of per record: written for contracts in code that read many records (a `git status` of a large tree). After a failure no later batch is passed; the records of the failing batch after the failure point are not read by the contract.
- Route contracts declare `OnRecord`, and may also declare an `OnBatch` with the same meaning: routed calls and shadow replays (`Measure-OPumper2Contract`) then use `OnBatch`. The Git status contract and the catalogue filter contracts declare both.
- `OnStdOut` / `OnStdErr`: `param($line, $state)`; delimiters define frames, so a frame need not be a line.
- `Complete`: `param($state, $execution)`; returns one domain value for the final object's `Data`.

Callbacks may emit domain objects. The final object has `Kind = Completion`, `SchemaVersion` (2), `Outcome`, `Data`, `Execution`, `Error`, `Completeness`, `Truncation`, `Measurement` and `Capture`. Native nonzero exit codes are interpreted using `SuccessExitCodes`; a changed working tree need not be an execution failure. `Error` has `Code`, `Phase`, `ExceptionType` and `Message`, the exception's message when an exception caused the failure.

Record callbacks, finalizers and task bodies share the same boundary: diagnostic streams become a structured callback failure. Callback code executes synchronously and must return cooperatively; the native timeout cannot interrupt arbitrary PowerShell callback code.

Every native completion, successful or not, carries `Capture`, and `Execution.Timing` (the phase durations of the call, see [measurement](doc/MEASUREMENT.md)), which stays on the local object like `Capture`: `Stdout` and `Stderr` are the complete decoded streams, `Complete` is true only when both streams were read to EOF and fully captured, and `Lossy` is true when invalid bytes were replaced while decoding. Timeouts, cancellation and decoder failures yield partial text with `Complete = false`; a call that never started yields null text. Framing does not apply: oversized records and lines after a callback failure are included. There is no size limit, so memory grows with the output. `Capture` lives on the local object only: a local script keeps the object (`$result = pump -AsObject ...`), branches on `$result.Outcome` and extracts what its contract did not keep, without running the command again.

JSON and YAML deliveries of an unsuccessful completion carry an `Excerpt` of the capture instead; a successful delivery carries none. For each non-empty stream, `Stdout` and `Stderr` hold `Lines` (the stream's line count) and `Tail` (its last `ExcerptLines` lines, 20 by default, each cut to 1000 characters and then ending with `…`). `Complete: false` and `Lossy: true` are repeated when they apply. Excerpt lines pass through the obfuscation pipe. `ExcerptLines` 0 delivers no excerpt.

`New-OPumper2Result` implements the Result pattern for handlers and local scripts. `-Completion` wraps an engine completion in a copy that keeps its outcome, execution, error, completeness, measurement and capture; `-Data` replaces its domain value. Without `-Completion`, `-Outcome`, `-ErrorCode` (default `HandlerFailed`, phase `Handler`) and `-ErrorMessage` describe a fresh result, accounted as a step of the current task. `-Projection { param($data, $settings) }` computes the `Data` of JSON and YAML deliveries from the complete value; `$settings` holds the delivery's `Format`, `MaxItems`, `MaxOutputBytes`, `ExcerptLines`, `Envelope` (a copy of the completion being delivered) and `Compact`; `Limit-OPumper2Projection $projection <names> $settings` bounds named lists of a projection to `MaxItems`, then to the byte budget, counting what went in `Omitted`. `-AsObject` keeps the complete value, and the presentation itself is never delivered. A failing projection omits `Data` and reports `ProjectionFailed`. `-ExcerptLines` narrows the excerpt of the result's failure, for example to 0 when its `Data` already explains the failure; it never widens the delivery's window.

`WorkingDirectory` resolves a relative path against the PowerShell location; route handlers receive it absolute.

A finalizer failure is also retained as `Execution.FinalizerError`. It does not overwrite an existing native failure, timeout or cancellation; composed task issues preserve both diagnostics.

`AsObject`, `AsJson` and `AsYaml` are exclusive. Objects preserve their shape and are not subjected to presentation limits: an `-AsObject` value is for the local script that keeps it in a variable, never for the output, since it holds the complete `Capture`, the domain `Data`, the `Presentation` scriptblocks and methods. `Out-OPumper2` is the delivery boundary of such a script: piped values ending with a completion are delivered as `pump` would have delivered them (recalled, measured, bounded, masked); any other values become the `Data` of a successful result. It takes `-AsJson`/`-AsYaml` (the configured format otherwise, YAML when that is `object`), `-MaxItems`, `-MaxOutputBytes` and `-ExcerptLines`. Serialized output is one sequence/document, including its completion object. UTF-8 budgets cover the actual final text. Omission is explicit and never silently reported as complete.

Delivered completions omit default metadata: null, false, zero, empty strings and empty collections, the initial `NotDelivered` measurement status (a completion never recorded as a delivery, such as a `Get-OPumper2Gain` report), and true for the completeness flags (`Completeness.Source`, `Completeness.Analysis`, the issues' `Source` and `Analysis`, `Excerpt.Complete`). An absent field therefore has its default value. A known `ExitCode` (0 included) and a non-null `Data` are always present. Records and `Data` are never compacted, and objects keep every field.

Presentation limits bound emitted records, then serialized bytes. They do not silently trim arrays inside the caller's freely defined `Data`. Recursive protection has a depth limit, reported as `DepthLimit` when applied. When the byte budget is exceeded, records are removed first (newest first), then `Data`, then excerpt lines (the oldest line of the longest tail, the earliest tail on ties), and finally only minimal metadata is delivered.

`Truncation.Reasons` accumulates without duplicates and `OmittedRecords` sums every omitted record: `ItemLimit` (beyond `MaxItems`), `OutputLimit` (records removed for the byte budget), `DataLimit` (`Data` dropped for the byte budget), `ExcerptLimit` (an excerpt line was cut or removed for the byte budget), `DepthLimit`, `ObfuscationFailed`, `ProjectionFailed` and the native `RecordLimit`. `MetadataLimit` alone means only minimal metadata fitted; it supersedes the other reasons.

Serialized deliveries pass through the ordered [obfuscation pipe](doc/OBFUSCATION.md): records, `Data`, excerpt lines and error messages are masked; other engine metadata and `AsObject` values are not.

`Invoke-OPumper2Task` collects local direct/routed calls, preserves failures even when their values are assigned or ignored, and produces a single completion with a freely projected `Data`. It associates all source calls with one serialized delivery. Its `Outcome` is that of the first unsuccessful step in execution order; a failing task body yields `Failed` only when every earlier step succeeded. `Error` describes the task body, and `Execution.Issues` lists up to 20 unsuccessful steps in order, each with its `Outcome`, `ExitCode`, `Error`, `FinalizerError`, completeness flags, `Truncated` and `Capture` (delivered as `Excerpt`).

Configuration: `~/.opumper2/config.yaml` (or `OPUMPER2_CONFIG_PATH`), a mapping of sections: `general` holds the settings below, `pumps` the contributors `Import-OPumper2Workspace` loads; any other section is an error. `general`: `outputFormat: yaml`, `maxItems: 20`, `maxOutputBytes: 8192`, `timeoutSeconds: 600`, `excerptLines: 20`, `databasePath: ~/.opumper2/db.sqlite`, `tokenizer: o200k_base`. Measurement history ([measurement](doc/MEASUREMENT.md)): `retentionDays: 90`, `recallWindowMinutes: 30`, `measureAlternateFormat: false`, `sessionVariable: OPUMPER2_SESSION`, `tracking: true`, and optionally `tokenPrice`, `currency: USD`, `monthlyTokenBudget`, `quotaTiers` and `quotaTier`. Delivery: `envelope: full` or `compact`. [Recall store](doc/RECALL.md): `recall: on` (or `failures`, `off`), `recallRetentionDays: 30`, `recallMaxEntries: 200`, `recallMaxEntryBytes: 10485760`, `recallMask: true`. Agent hooks: `hookAwareness: warn` (or `off`, `deny`, `rewrite`) and `hookExcludeCommands: []` (wildcard patterns). Explicit parameters override configuration. `OPUMPER2_CONFIG_PATH` selects another configuration file; `OPUMPER2_TRACKING=0`, `OPUMPER2_RECALL=0` and `OPUMPER2_HOOK=0` switch tracking, the recall store and agent hooks off for one process. `Get-OPumper2Configuration` returns the effective configuration.

Delivered completions name their stored output in `Recall` (absent for `-AsObject` and when the store is off). Read it with `Get-OPumper2Recall <id>` rather than running the command again.
